# SDD: AI Growth Mirror v1.0.2 DDD 可解释评估与新工具接入

English version: [v1.0.2-DESIGN.md](../en/design/v1.0.2-DESIGN.md)

> 本文承接已冻结 Spec。多轮设计 Review 已关闭全部 P0；只有本文定义的主链、真源与验收可派生实现任务。

## 1. 目标、边界与不做条件

- 用户结果：DeepSeek Harness、ZCode 的根任务可进入统一分析；用户看到分数、证据覆盖、主要原因、训练动作与下期回看，而不是只看到结论。
- 架构结果：Session Observation、Growth Assessment、Learning Loop 三个 bounded context 各自拥有模型与规则；外部格式通过 ACL 进入领域。
- 真源结果：评分政策、工具目录、分析单位、报告主编排各有一个 owner；投影只读，不复制规则。
- 不做：不全仓形式化重写，不解析 reasoning，不读 ZCode model-io headers，不新增第七轴，不保留旧评分并行兼容层，不发布或推送。
- 停止条件：未知外部格式、跨 policy 对比、schema 缺失、隐私边界无法证明时 fail closed；不得猜测或降级到第二真源。

## 2. 限界上下文与统一语言

| Context | 核心职责 | 领域对象 | 入站/出站边界 | 禁止事项 |
|---|---|---|---|---|
| Session Observation | 把不同工具事实归一为一次用户可见根任务 | `SessionRecord`、`SessionRead`、`RootTaskId`、`ReaderDiagnostic` | `SessionReaderPort`；外部 reader ACL | 评分、文案、执行原始命令、持有 cache/adapter |
| Growth Assessment | 从会话事实计算六轴、总分、等级、证据覆盖和原因码 | `MetricObservation`、`AxisComponent`、`AxisAssessment`、`GrowthProfile` | `AssessmentService` | I/O、工具专属分支、自然语言解释、第二公式 |
| Learning Loop | 从弱证据生成最多两项训练契约，并按同策略回看 | `ActionContract`、`TrainingOutcome`、`PolicyComparable` | snapshot/comparison ports | 跨 policy 强算 delta、泛化鸡汤 |
| Reporting（Application） | 编排 collect→assess→explain→persist | request/result/view model | declared ports + composition root | 复制领域公式、第二报告流水线 |

统一语言：`root task` 是用户可见任务；`child session` 是委派执行证据；`missing` 是未观测，不是失败或满分；`coverage` 是可用 component 权重占比；`confidence` 是证据数量、分母与来源质量的函数；`policy version` 是评分语义身份，不等于产品版本。

## 3. 依赖方向与目录设计

```text
cli ──> application/orchestrator ──> domain/growth + domain/session
             ^          |
             |          v (ports)
        composition root <── infra/readers + cache + snapshots + render/io

external DeepSeek/ZCode ──> infra ACL ──> SessionRecord ──> AssessmentService
```

目标切片：

```text
ai_growth_mirror/
  domain/
    session/model.py                 # 纯 SessionRecord；无 adapter/cache/I/O
    growth/assessment_policy.py      # 唯一 policy version/轴权重/阈值/component 定义
    growth/assessment.py             # 值对象 + AssessmentService
    growth/scorer.py                 # 聚合事实，调用唯一 AssessmentService
    growth/capability.py             # 只投影 AxisAssessment，不含备用公式
    snapshots/comparison.py          # 从 policy owner 读取权重，先判可比性
  application/
    orchestrator.py                  # 唯一业务编排
    explanation_service.py           # reason code → i18n view，不计算分数
  infra/readers/
    catalog.py                       # 唯一 tool id/alias/adapter catalog
    deepseek_harness.py              # v0 JSONL/Zstd ACL
    zcode.py                         # SQLite ACL
```

不新建第二个公开 pipeline。`application/orchestrator.generate_report_artifacts` 仍是唯一业务主编排；CLI/composition 只组装端口并调用它。application 与 infra 的现有直接依赖以本次涉及主链为 hard cut 边界，领域层必须零 infra/application import，并用 AST gate 阻断回潮。

## 4. 核心设计

### 4.1 评分政策唯一真源

`domain/growth/assessment_policy.py` 唯一声明：

- `ASSESSMENT_POLICY_VERSION = "2.0"`；
- 六轴顺序和权重：协作建模 14%、执行驱动 25%、实现深度 19%、交付闭环 19%、适应恢复 10%、Agentic 系统化 13%；
- 等级阈值、每轴 component 权重、最低 coverage/evidence；
- 归一化、饱和和 confidence 参数。

scorer、capability、snapshot、comparison、report、tests 均 import owner 或消费 owner 产出的 `AxisAssessment`，禁止复制字典。结构测试扫描第二份权重/阈值和旧公式；cross-policy comparison 在计算前返回 `incomparable`。

### 4.2 观测和值对象

```python
MetricObservation(
    value: float | None,              # 0..100；未观测为 None
    available: bool,
    evidence_count: int,
    denominator: int | None,
    confidence: float,                # 0..1
    reason_codes: tuple[str, ...],
)

AxisAssessment(
    axis_key: str,
    score: float | None,
    coverage: float,
    confidence: float,
    components: tuple[AxisComponent, ...],
)
```

- component 缺失时从分母动态排除并对可用权重重归一；低于轴最小 coverage 时整轴 unavailable。
- 真实观测为 0 必须保留为 0，不能与 missing 混淆。
- 总分只对 available axes 重归一；无任何轴时总分/等级 unavailable。
- explanation 仅携带稳定 reason code 和数值；中文/英文句子由 application i18n 生成。

### 4.3 六轴计算与因果边界

| 轴 | component（轴内权重） | 可用条件 | 明确不计入 |
|---|---|---|---|
| 协作建模 | effective contract 40%、context grounding 25%、goal locking 20%、opportunity-conditioned clarification 15% | contract/context/goal/clarification 至少达到最低 coverage | contract 二次奖励、无 goal 默认 100 |
| 执行驱动 | autonomous chain 35%、structured workflow 30%、verified continuation 20%、delegation success 15% | 每项有对应事件；委派必须有结果且根任务验证 | subagent/tool 调用次数 |
| 实现深度 | implementation-session rate 30%、code verification 35%、fully-achieved rate 20%、files/session saturated 15% | 至少有实现或验证证据 | token 总量、总文件数、模型/工具种类 |
| 交付闭环 | fully achieved 40%、verification 25%、test 15%、contract compliance 20% | compliance 仅 denominator>0 | commit 数、无 contract 默认 100 |
| 适应恢复 | recovery success 50%、correction quality 25%、post-friction verification 25% | 存在 error/偏航/中断/resistance opportunity；不足则 unavailable/低置信 | 没遇到问题送分 |
| Agentic 系统化 | skill 18%、workflow 18%、structured 14%、reuse depth 15%、asset authoring 12%、assetized 10%、advanced feature 8%、method saturation 5% | 方法存在且至少绑定交付/验证结果 | MCP/Hook/Goal/Plan/Skill/模型种类的裸次数 |

总分不再使用 asset bonus、consistency modifier、L4/L5 floor promotion。原始 usage 只进入成本/强度解释。文件数 component 在小区间饱和，仅作辅助，并由 anti-gaming 用例保证超过饱和点不涨分。

### 4.4 Root task 聚合

1. reader 先索引会话 header/metadata，构造 parent→children 图。
2. root 仅取用户可见根会话；孤儿 child 输出诊断并跳过，不猜归属。
3. 根会话用户/助手轮次保持原语义；child 的工具、usage、验证、Skill/Goal/Plan/委派结果汇总一次。
4. 每个 physical session 只进入一个 root roll-up；用 `session_id` 去重，环和重复 parent fail closed。
5. 多层 child 递归汇总；深度有安全上限并产生诊断。

### 4.5 DeepSeek Harness ACL

- 默认根：`~/.dsh/sessions/**/session.jsonl.zstd`，同时支持配置的 raw `.jsonl`。
- 使用 `zstandard` 流式 reader 支持 concatenated frames，不将整个文件读入内存。
- 第一条必须是 `type=session` 且 `version=0`；logical rows 使用 `seq/time/data`，校验 seq 单调且唯一。
- 消费 `user/message` 的真实 `source.kind=user` 内容、`assistant/message.usage`、`request/context.model`、`tool/call`、`tool/result.error`、`goal/change`、`todo/write` 与 `compaction/start`；其它 logical event 仅维持顺序/生命周期，packed `*-chunks` 不作为业务事实。
- 根会话的真实用户消息保留为协作输入；child 的委派提示不冒充人类消息。Goal/Todo 投影为结构化工作流信号，tool-call chain、首次写入轮次、验证命令与 usage 进入统一事实；空 seed root 计 `skipped`，不进入评分。
- 未知 version、坏 header、seq 破坏、解压失败只跳过该会话并计入诊断；异常和日志不得包含正文。

### 4.6 ZCode ACL

- 默认真源：`~/.zcode/cli/db/db.sqlite`；通过 SQLite URI `mode=ro` 打开，不触发 migration/write。
- capability probe 固定 required table/column；v1.0.2 只读取已冻结的 `session/message/part/tool_usage/model_usage` 投影。`turn_usage/session_target/session_task_link` 即使存在也不是本版评分真源，后续接入必须先扩展版本化契约。
- `message.role` 与 `part.type=text/tool/reasoning/step-finish` 映射统一事实；reasoning 只计存在性，不读取/输出内容。
- root/child 从 parent/session link 构图；Goal/Task link/工具结果/usage 向根汇总。
- `tasks-index.sqlite` 不是 transcript；`rollout/model-io-*.jsonl` 含请求/响应 headers/body，被安全策略显式禁止作为 fallback。
- 缺表/列、busy/locked、坏 JSON 产生 `schema_mismatch/unreadable/corrupt` 计数，其它 reader 继续。

### 4.7 解释与训练闭环

每轴 report/sidecar 展示：policy version、score/unavailable、coverage、confidence、最多两个正向与两个短板 component、证据数量、稳定 reason code 对应的人类解释。不得输出原始 prompt/reasoning/tool result。

Action Contract 由最低的 available component 驱动，最多两项，每项固定：`why`、`next_action`、`success_signal`、`next_period_check`。Learning Loop 在下一期按相同 policy 回看 `not_observed/attempted/effective/ineffective`；跨 policy 只建立新基线。

### 4.8 诊断与目录

reader catalog 是 `tool_id/aliases/default_roots/adapter factory` 的唯一 owner。CLI choices、`all`、status 和文档测试由 catalog 派生；alias 只做输入规范化。

每个 reader 输出 `detected/parsed/skipped/corrupt/schema_mismatch/orphan` 汇总。日志只含 tool id、错误码、计数和安全相对标识，不含消息、SQL 参数正文、headers 或密钥。

## 5. 数据、版本与迁移

- Product 目标版本：1.0.2；Cache Schema 维持 1.0，因为 SessionRecord/SessionRead 持久 shape 不变。
- snapshot/profile/sidecar 新增 `assessment_policy_version`、axis components/coverage/confidence；旧 snapshot 无 policy 字段时视为 `legacy/uncomparable`。
- 不双写旧新评分；升级后新报告只产生 policy 2.0。旧 snapshot 保留只读，形成明确历史断点。
- 若实现证明 cache shape 必须变化，立即停止并回到 Spec 升级 Cache Schema，不在代码中隐式容错。

## 8. 四高二低三底座取舍

| 透镜 | 暴露的问题 | 设计决策 | 验证 |
|---|---|---|---|
| 高价值 | 分数无法说明原因 | component evidence → reason → action → next check | user-visible snapshot |
| 高可信 | missing 送分、体量送分、跨策略伪趋势 | availability、anti-gaming、policy gate | metamorphic/calibration |
| 高性能 | 大 Zstd 与 SQLite 全扫 | header index、流式、root 定向 roll-up | latency/memory budget |
| 高演进 | preview/schema 变化 | ACL capability probe，拒绝猜测 | unknown-version/schema tests |
| 低上下文 | 权重/工具列表/公式重复 | policy/catalog 单 owner | drift tests |
| 低变更 | 全仓 DDD 与双写风险 | 主链 hard cut、Schema 1.0、无兼容壳 | diff/layer tests |
| 可维护 | 巨型 scorer、domain I/O | 值对象、领域服务、ACL | dependency test |
| 安全 | 会话正文/headers/执行注入 | 只读、最小化、禁止 fallback/执行 | canary/negative tests |
| 可观测 | 静默 skip、轴证据不明 | structured diagnostics + coverage/confidence | diagnostics/report tests |

## 10. 回退

- reader：可从 catalog 移除未发布 adapter，但不得 fallback 到未授权来源或猜字段。
- scoring：可以通过新 ADR 发布下一 policy version；不得原地修改 2.0 后仍宣称可比。
- DDD：回退实现时不得恢复 domain→infra 或第二评分公式。
- snapshots：保留旧文件；不同 policy 只读展示，不删除、不改写。
